## Blockers before production (owner decisions)

1. **Hosting accounts:** an EU staging server (Denmark testing) and a Pakistani production server that meet the [deployment runbook](DEPLOYMENT.md) requirements.
2. **Domain and DNS:** `gas365.pk` (planned) and `staging.gas365.pk`.
3. **Transactional email:** an SMTP provider plus SPF, DKIM and DMARC on the domain.
4. **Off-site backup storage:** an rclone remote, plus a heartbeat monitor.
5. **GitHub environments:** staging and production, with a required reviewer on production and the deploy secrets.
6. **Legal and tax:** FBR and sales-tax applicability, invoice wording and data-retention periods for audit and financial records. These are open in the [risk register](RISKS.md); until decided, records are kept indefinitely.
7. **Administrator sign-in hardening:** optional MFA for owners and platform administrators remains open.
8. **Pilot data:** real-data cutover and reconciliation of opening balances with each pilot business. The import tooling is ready.

## Staging acceptance steps (once hosting exists)

1. Prepare the server following the runbook.
2. Merge to `main` and confirm the automatic staging deployment.
3. Verify `https://staging.gas365.pk/health/ready` returns `Healthy`.
4. Run the Playwright suite against staging with `WEB_URL`.
5. Run `backup.sh`, then `restore.sh` into a scratch database, and compare counts.
6. Run `scripts/load-test.mjs` against staging with `WEB_URL`, in a quiet window.
7. Record results in the next phase report. Only then consider a production release, through the approval-gated workflow.
